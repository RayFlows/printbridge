# PrintBridge · 印桥

面向微信的自托管打印项目。目标是在微信里完成选文件、文档预览、打印设置和引导式手动双面打印，由树莓派或其他 Linux 设备通过 CUPS 驱动打印机。

**已实现扫码授权、文档/图片转换预览、打印设置、持久化任务和手动双面确认流程。**
小程序模拟器以及树莓派的 PDF、图片和常见 Office 格式转换预览已用合成文件验收；
手机、正式入口和实际出纸仍待完成。
路线及验证边界见 [增量计划](docs/roadmap.md)。

## 当前能力

- Go 服务启动、配置校验和 JSON 日志。
- `GET /healthz`：进程存活检查，不代表 CUPS、打印机或文档转换工具可用。
- `GET /api/v1/server`：服务名称、构建版本、API 版本。
- HTTP 请求平滑退出、超时退出，以及对应自动测试。
- 扫码后自动用码内打印访问凭据换取有限期会话，用户无需输入地址或配对码。
- 原生微信小程序的扫码入口、打印机列表、能力展开、刷新和故障状态。
- 部署者可用独立工具请求微信生成小程序码；已覆盖模拟接口，真实账号出码和手机入口尚未验收。
- IPP 适配器连接现有 CUPS，读取能力、保持提交、核对状态和取消作业。
- 微信聊天选择单个文档或图片，也可从相册取图，不提供拍照入口；上传后在同一设置页预览、翻页、放大、重新上传；项目界面尺寸使用 rpx。
- SQLite 文档元数据、会话归属、按需预览缓存、资源限制与过期清理；上传和预览不打印。
- PDF、DOC/DOCX、XLS/XLSX、PPT/PPTX、ODF、RTF、TXT/CSV 和常用图片转换到同一 PDF 流程。
- 纸张、颜色、份数、范围、奇偶、倒序、方向、缩放、多页合一、自动/手动双面，打印前查看最终纸面和正反面对应。
- 明确确认后提交；查看任务、请求取消、翻纸后继续。持久化会话与任务在有效期内跨重启恢复，未知提交先核对而不盲目重发。
- 可选 Canon IVEC 回传适配器，把缺纸状态接入 CUPS；任务页支持缺纸弹窗。
  已通过树莓派隔离 CUPS 验证，正式启用及实体补纸续打状态见部署验证记录。
- Windows / Linux Go 检查、Linux ARM64 交叉编译和小程序类型/行为检查的 CI 配置。

## 本地运行

需要 Go 1.26 或更高版本。预览需要 Poppler 的 `pdfinfo` / `pdftoppm`，Office 转换另需 LibreOffice 与文档所需字体，
缺少工具时文档接口明确报错，其他接口仍可运行。

```sh
cd server
go run ./cmd/printbridge
```

服务默认监听 `127.0.0.1:8080`。检查响应：

```sh
curl http://127.0.0.1:8080/healthz
curl http://127.0.0.1:8080/api/v1/server
```

当前开发版本返回：

```json
{"name":"PrintBridge","version":"dev","apiVersion":"v1"}
```

配置、配对码生成、构建和检查命令见 [开发说明](docs/development.md)。
已有 CUPS 的树莓派安装及用户级 systemd 管理见 [部署说明](docs/deployment.md)。
小程序导入步骤见 [客户端说明](miniprogram/README.md)。默认未设置配对码，只能访问公共元信息。
配置配对后，客户端才能读取 CUPS 队列；没有 CUPS 时返回明确错误，不提供模拟成功结果。

## 目标体验

扫打印机旁的小程序码，直接进入打印流程，选择微信聊天文件，等待转换和预览，调整页码、纸张、份数等设置，确认打印。手动双面时在微信里提示翻纸，用户放好纸后继续背面。

文档只需上传一次。预览和打印围绕同一份准备好的文档进行，服务端负责页面安排和任务状态。设备连接、文档处理和任务调度独立维护，微信界面不承担页序算法。

第一版以同一局域网为部署目标。小程序的正式发布、扫码入口和手机网络行为需要用实际账号及真机验证；本仓库不宣称这些环节已经通过验收。

## 仓库结构

| 路径 | 职责 |
| --- | --- |
| `server/` | Go 服务、配对、文档生命周期、页面安排、持久化打印、SQLite、文档工具、CUPS 和 HTTP |
| `miniprogram/` | 原生 TypeScript 小程序、TDesign 组件依赖、网络服务和页面行为检查 |
| `api/openapi.json` | 已实现 HTTP 接口的 OpenAPI 契约 |
| `docs/architecture.md` | 模块职责、依赖方向、扩展方式 |
| `docs/roadmap.md` | 每个增量的范围、验收条件和状态 |
| `docs/decisions/` | 影响维护成本的架构决策 |
| `deploy/` | 用户服务安装、文档依赖安装和只做预览的部署检查 |
| `.github/workflows/` | 自动检查配置 |

目录随实际实现建立，计划中的模块不会用空实现冒充已完成能力。

## 参与开发

先阅读 [架构](docs/architecture.md) 和 [开发说明](docs/development.md)。每个增量都应包含一条可验证的流程、对应测试和必要文档，并保持此前增量可用。

新增文件类型时扩展文档处理；新增打印机差异时扩展设备能力及校准资料；新增客户端时调用同一套 API。不要把这些变化混入同一个 HTTP handler 或页面组件。
