## 现有 CUPS 只读联调

人工验证与自动测试分开：在 Windows 启动编译后的 PrintBridge，用临时 SSH 本地隧道访问树莓派
现有 CUPS。树莓派架构返回 `aarch64`。

完成配对后，`GET /api/v1/printers` 读到 `Canon_G2810` 及现有 `Canon_G2810_even`、
`Canon_G2810_odd` 三个队列。主队列报告：

- 驱动模型：`Canon G2000 series - CUPS+Gutenprint v5.3.4`。
- 队列空闲且接受任务；这不是纸张或物理设备就绪验证。
- 单双面：`one-sided`。
- 颜色：`monochrome`、`color`。
- 纸张能力：93 个已报告的 media 值。

撤销会话后，同一令牌读取队列返回 HTTP 401。未保存配对码、令牌、私钥路径或完整二维码到仓库。
检查结束后已停止临时 PrintBridge 进程和 SSH 隧道。
整个流程仅查询队列/能力，没有提交、取消或修改打印作业，没有改队列或驱动。

## 同日启动故障修复

用户截图显示 `tdesign-miniprogram/input/input` 在小程序运行路径下找不到组件。
连续两次文件探针均确认安装目录存在组件，而 `src/miniprogram_npm` 中缺少产物。
原页面测试只检查安装目录；改为运行目录后，准确复现同一缺文件错误。
新增准备流程测试也先复现了“setup 成功但未生成组件”的错误，再修改脚本。

修复后执行 `npm run setup`，实际生成原生组件、内嵌依赖和许可；真实本地项目配置的
SHA-256 在执行前后相同。`npm run check` 和全部 21 项客户端测试通过。
测试还验证重复准备清理旧产物、不覆盖本地配置、缺少安装依赖时非零退出并给出安装指引。
没有修改服务端或执行打印操作。具体构建职责见 [ADR 0003](../decisions/0003-native-component-preparation.md)。

## 同日扫码交互修正

产品反馈指出手工填写地址和配对码不符合“一次扫码直接进入”的要求。
先把页面回归条件改成“小程序内扫码自动进入”和“微信入口参数免二次扫码”：
旧实现两项均失败，实际授权请求数为 0。修正后，两项与其他检查一起通过。

本轮移除地址和配对表单，二维码 v2 自动提供服务地址和独立打印访问码。
生成工具构造官方 `getwxacode` 请求；生成请求中的实际 path 经客户端真实解析器还原后，
保留地址及带百分号、加号等特殊字符的测试凭据，不发生二次解码。
HTTP 会话请求/响应保持原契约，没有增加任何打印接口。

最终检查：

- `npm run check` 通过；全部 40 项客户端测试通过。
- 覆盖外部入口冷/热启动、普通前后台恢复不重复授权、再次扫码、取消、更换和网络重试。
