# ADR 0002：设备配对、能力读取和原生客户端

日期：2026-10-14。状态：采纳，M1 代码已实现，客户端运行时验收待完成。
其中“仅地址二维码 + 手工配对”的入口决策已由 [ADR 0004](0004-scan-entry.md) 替代；
会话机制、CUPS 适配和客户端技术选型继续适用。

## 决策

服务部署者设置独立的设备配对码，客户端用它换取随机会话令牌。配对码不是 CUPS 管理密码，
也不是微信 AppSecret。缺少配对码时服务仍提供存活和版本接口，但拒绝配对及设备访问。
默认会话有效期 24 小时；M1 仅在进程内保存令牌摘要，重启撤销全部会话。
将来持久化任务时再决定会话持久化，当前不引入只有一个空表的数据库。

配对限制为每个服务每分钟 10 次尝试，同时最多 128 个有效会话；限制作用于整个设备，
不是按客户端 IP，避免依赖不可信的代理头。重启会清除限制，也撤销原会话。
退出连接会撤销当前令牌。配对码轮换后重启撤销所有设备会话。
局域网 HTTP 不提供传输保密，只适合可信网络；HTTPS 可用于已有证书和域名的部署。
远程公开访问、用户账号、权限分级不属于 M1。

原入口采用“只含地址的二维码，再手工配对”。该交互不符合一次扫码直接打印的产品要求，
已停用；新版由打印码携带独立访问凭据并自动换取会话，具体契约见 ADR 0004。

通过 OpenPrinting `goipp` 编码 IPP，发送只读 `CUPS-Get-Printers` 操作。
`cups` 适配器返回独立的打印机领域数据，由 HTTP 接口输出；不向客户端开放任意 CUPS URL 或 IPP 操作。
缺失能力返回空集合或 null，不能从型号猜测双面、纸张或颜色支持。
CUPS 队列状态仅表示队列报告，不等于设备有纸或已完成物理打印。

## 小程序基础

采用原生 TypeScript，按需使用 MIT 许可的 `tdesign-miniprogram` 组件。
参考微信官方 `miniprogram-demo` 的平台组织方式；不复制示例的业务代码。
腾讯零售模板包含商品、购物车、订单等领域，与本项目不匹配，因此不整体导入。
页面依赖 `services/`，网络、会话、响应校验都留在服务层；领域层不依赖微信 API。

## 后果

M1 无需微信身份服务器或 AppSecret 即可验证服务连接，文件选择及预览在 M2 接入。
设备的访问码需要部署时生成并通过打印码分发，之后客户端只保存有限期会话。
小程序组件通过锁文件更新，不建立模板分支长期追随无关业务。
