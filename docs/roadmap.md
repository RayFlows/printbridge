# 增量计划

每个增量完成一条可演示、可验证的流程，并保持此前能力可用。
“已完成”需要代码、相关测试和文档均通过检查；真机验收与自动测试分别记录。

2026-10-14 用户明确要求完整打印体验：增量是内部开发方法，不是 PDF-only 的产品范围。
当前工作前置 M5 常见文档/图片输入，并继续贯通 M3/M4 的设置、提交、状态、取消和翻纸确认。
完成标准仍包含各功能失败处理与测试，不能以只能预览 PDF 作为整项需求的交付。

| M3 单面打印 | 设置参数、确认打印、查看与取消任务 | 本地及树莓派虚拟设备验收完成，真实打印待验收 |

## M0：基础工程

范围：模块约定、Go 启动程序、存活/版本接口、配置校验、生命周期、OpenAPI 和 CI。

验收：

- Windows 上能启动、查询、停止服务，非法配置明确失败。
- HTTP 方法及错误响应符合契约，版本可在构建时注入。
- 停机允许已有请求完成，超时后关闭剩余连接。
- `gofmt`、`go vet`、带 race 的测试通过，能交叉编译 Linux ARM64。
- 明确写出尚未实现的功能，不创建 CUPS 作业。

本地验收于 2026-10-13 完成，详见 [M0 验证记录](verification/2026-10-13-m0.md)。
GitHub 托管 CI 和树莓派运行尚未验证，不包含在本地验收结论中。

## M1：扫码入口

从微信扫码进入，按需在微信原生弹窗完成隐私确认后列出 CUPS 打印机及能力。先做只读流程。
连接入口和客户端错误处理在这个增量就接入，避免后端长期脱离真机开发。
普通用户不输入 IP、服务地址或配对码。从微信入口码进入时不得再次要求扫码。
直接从“最近使用”打开且没有有效会话时，只提供扫码入口；有有效会话则恢复打印机页。

验收：失效会话、错误地址、CUPS 不可用均有明确结果；开发工具及手机分别验证。
确认普通用户的小程序入口方式，保存不含账号秘密的验证记录。不能用开发者工具的
“跳过域名校验”结果替代真机测试。

本次实现：原生 TypeScript + 按需 TDesign 组件；二维码携带独立打印访问码，
自动换取有期限的会话，读取 CUPS 队列和其报告的能力，支持刷新、扫码切换和退出。
二维码解析和会话交换在 `services/`；微信入口参数及小程序内扫码共用同一流程。
部署者工具调用微信 `getwxacode` 生成入口码，真实调用需要有效的小程序服务端 access token。
没有上传或打印接口。

已完成：后端行为/并发检查、模拟 IPP 联调、客户端类型/行为检查、WXML/WXSS 离线编译，
以及 Windows 服务通过 SSH 隧道读取现有 CUPS 的只读联调。
2026-10-14 修复启动时缺少 TDesign 组件的问题：`setup` 现在准备真实运行文件，
CI 和回归测试检查 `src/miniprogram_npm`，不再只检查 `node_modules`。
同日按产品反馈去掉地址/配对表单，加入自动扫码授权及入口码生成工具。
生成码与自动进入的检查使用模拟微信接口和 `wx`；不视为真实微信出码或扫码验收。
另已准备开发者工具的私有“本地调试（自动授权）”启动项，便于先试用打印机列表；
入口参数经真实客户端服务代码读取现有 CUPS 验证。
同日后续通过开发工具界面完成实际编译、自动授权和打印机列表布局验收，
详见 [移动端修正验证](verification/2026-10-14-mobile-options.md)；CLI 连接失败不再作为模拟器验收结论。
未完成：真实账号生成小程序码、手机网络与普通用户入口验收。
此阶段尚未把 PrintBridge 部署到树莓派；后续部署及 ARM 实测见 M6，
不能把读取树莓派 CUPS 和 ARM64 交叉编译写成服务端 ARM 实测。
详见 [M1 验证记录](verification/2026-10-14-m1.md)。

## M2：PDF 准备

加入文档生命周期、SQLite 迁移、受授权的上传与分页预览，小程序可翻页、放大。
上传只产生文档编号，不产生打印任务。

首次交付范围：单个 PDF，最多 20 MiB / 500 页，服务端按需生成分页图；
文档只属于上传时的会话，默认保留 24 小时。页面参考 cups-web 的文件信息与纸张预览布局，
使用原生微信组件与 TDesign，项目自身的界面尺寸统一为 rpx。

验收：页数正确；上传和转换有大小及时间限制；失效授权无法下载文档；
失败输出不进入可用状态；相同文档不因翻页而重复上传；过期文件可清理。

2026-10-14 已完成服务端、原生页面和契约：SQLite schema 1、受授权上传、
页数解析、服务端分页缓存、微信下载缓存与放大、错误重试、过期清理。
本地检查包括 Go vet / race、50 项客户端检查、三个页面 WXML/WXSS 离线编译、
真实 Poppler 合成 PDF 渲染，以及 Windows HTTP 服务从上传到分页图和撤销授权的联调。
Windows 与 Linux ARM64 构建通过；本机测试服务已更新，沿用私有自动授权启动项。
同日后续在模拟器验收上传、原稿预览和布局，记录见 [移动端修正验证](verification/2026-10-14-mobile-options.md)。
此阶段没有真实打印；尚未完成手机聊天选文件、正式域名和树莓派运行验收，
后续树莓派运行结果见 M6。
详见 [M2 验证记录](verification/2026-10-14-m2.md)。

## M3：单面打印

加入打印设置快照、页面安排、CUPS 提交/查询/取消、持久化恢复和任务进度页面。
份数、纸张、方向、缩放和页码选项以打印机可用能力为依据。

验收：使用模拟 CUPS 验证一次点击只创建一次任务；验证超时及崩溃后的不确定提交处理；
预览和打印引用同一准备结果；提交成功不被当成物理完成。
真实打印单独安排并明确指定文件和纸张，自动测试不向物理队列提交。

2026-10-14 已实现原生设置页、不可变 Plan 及最终纸面预览、持久化任务、幂等提交、
查询和取消。参数含纸张、颜色、份数、范围、奇偶、倒序、方向、缩放和 1/2/4/6/9/16 合一；
自动双面只在设备报告支持时提供。客户端通过 59 项行为/工程检查，五页 WXML/WXSS 离线编译。
服务端 vet/race、模拟 IPP、真实 PDF 布局及 Windows/ARM64 构建通过。
本地服务已更新到 `0.3.0-dev`，真实 CUPS 联调仅读取能力和准备预览，没有提交实体打印。
详见 [M3-M5 验证记录](verification/2026-10-14-m3-m5.md)。

## M4：手动双面

加入设备校准资料及翻纸引导。任务在等待翻纸时持久保存，重新进入小程序仍可继续。

验收：覆盖 1、2、3、16、17 页、非连续页码、不同份数及翻转方向；
独立断言每张纸的正反面，不仅断言页面总数。
模拟异常、重复继续和重启恢复。实机确认 G2810 进出纸及翻转方式，
未校准的机型不直接套用 G2810 的顺序。

2026-10-14 已实现背面顺序/额外旋转设置及用户确认、本机保存设备设置、阶段文件、
`awaiting_flip`、纸张确认、继续和取消。原始页选择只应用一次；
1/2/3/16/17 页、非连续范围、拼版补空白和多份的正反对应已测试。
完整 HTTP → SQLite → PDF → 虚拟 IPP 流程验证翻纸等待和服务重启后继续，
没有重复提交阶段作业。超时先核对、无法核对时保持可见状态。
当前设备设置是用户确认的配置，不是自动校准工具；G2810 的实际进出纸顺序仍未验收。
